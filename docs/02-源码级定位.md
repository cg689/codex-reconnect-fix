## 一、出站代理策略：两选一

`codex-rs/http-client/src/outbound_proxy.rs`

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum OutboundProxyPolicy {
    /// Preserve reqwest's built-in proxy behavior.
    ReqwestDefault,
    /// Resolve system/PAC/WPAD settings, then environment settings, then direct routing.
    RespectSystemProxy,
}
```

这两个变体的文档注释就是整个问题的答案：

| 策略 | 行为 |
| --- | --- |
| `ReqwestDefault` | 保留 `reqwest` 内置行为 —— 只看 `HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY` 环境变量，**不读操作系统代理设置** |
| `RespectSystemProxy` | 先解析系统 / PAC / WPAD 设置，再退回环境变量，最后才直连 |

`RespectSystemProxy` 的注释明确写了三段回退顺序 —— 这也是为什么开了开关之后，即使系统代理被关掉，只要环境变量还在就仍然能出网。

## 二、路由解析链

同一文件中的解析函数，串起来就是运行时决策流程：

```rust
pub fn resolve_proxy_route(&self, request_url: &str) -> OutboundProxyRoute {
    resolve_proxy_route(&ProcessEnv, request_url, self.outbound_proxy_policy, resolve_system_proxy)
}
```

关键中间结构：

```rust
#[derive(Clone, Hash, PartialEq, Eq)]
pub enum OutboundProxyRoute {
    /// Preserve the underlying transport's existing proxy behavior.
    TransportDefault,
    /// Connect directly and bypass transport-level proxy discovery.
    Direct,
    /// Connect through the selected proxy URL.
    Proxy { url: String, no_proxy: Option<String> },
}
```

```rust
enum SystemProxyDecision {
    Direct,
    Proxy { url: String },
    Unavailable { failure: RouteFailureClass },
}
```

决策落地：

- `route_from_system_decision(env, env_proxy_kind, decision)` —— 把系统代理决策转成最终路由；系统代理不可用时回退环境变量。
- `resolve_env_proxy_route(env, env_proxy_kind)` —— 按请求 scheme 从环境变量解析（`EnvProxyKind` 区分 `Http` / `Https` / **`SecureWebSocket`** / `Other`）。
- `resolve_platform_system_proxy(request_url, origin)` —— 按平台分发（Windows / macOS / 其他）。
- `HttpClientFactory::resolve_proxy_route_async` —— 不阻塞 Tokio worker 的异步版本。
- `cache_system_proxy_decision` / `cached_proxy_route` —— 系统代理决策有缓存。

### 顺带解释了「WebSocket」那半边

```rust
// proxy_resolution_url: ws/wss 会被转成 http/https 以复用系统代理 API
```

`EnvProxyKind` 里专门有一个 `SecureWebSocket` 变体，说明**对 WebSocket 连接也走同一套代理解析**。社区把现象归因到「WebSocket 不被代理支持」，其实是同一个原因的另一个切面：不是代理不支持 WebSocket，而是**代理压根没被后端进程用上**，那么走 `wss` 的插件通道自然一起失败。

## 三、开关本身

`codex-rs/features/src/lib.rs`

```rust
/// Respect host system proxy settings for Codex-owned network clients.
RespectSystemProxy,
```

集中注册表 `FEATURES` 里的元数据：

```rust
FeatureSpec {
    id: Feature::RespectSystemProxy,
    key: "respect_system_proxy",
    stage: Stage::UnderDevelopment,
    default_enabled: false,
},
```

三个要点：

1. **key 是 `respect_system_proxy`** —— 也就是 `config.toml` `[features]` 表里要写的键名。
2. **`default_enabled: false`** —— 默认关闭，所以「默认不读系统代理」不是 bug，是当前的设计选择。
3. **`stage: Stage::UnderDevelopment`** —— 所以启动日志会给黄色警告；本项目在 `config.example.toml` 里一并给出消除警告的开关。

默认集合的构造方式：

```rust
/// Starts with built-in defaults.
pub fn with_defaults() -> Self {
    let mut set = BTreeSet::new();
    for spec in FEATURES {
        if spec.default_enabled { set.insert(spec.id); }
    }
    Self { enabled: set, legacy_usages: BTreeSet::new() }
}
```

用户配置通过键名反向解析后覆盖默认值：

```rust
/// Keys accepted in `[features]` tables.
pub fn feature_for_key(key: &str) -> Option<Feature> {
    for spec in FEATURES {
        if spec.key == key { return Some(spec.id); }
    }
    legacy::feature_for_key(key)
}
```

查询则是集合成员判断：

```rust
impl Features {
    pub fn enabled(&self, f: Feature) -> bool {
        self.enabled.contains(&f)
    }
}
```

## 四、策略在配置解析处被读取

`codex-rs/core/src/config/mod.rs`

```rust
let respect_system_proxy = features.enabled(Feature::RespectSystemProxy);
```

这个布尔值最终被传进 `HttpClientFactory::new(outbound_proxy_policy)`，决定了客户端构建时用哪套 `route` 解析。

## 五、由源码得出的三条工程结论

1. **只改一行 `respect_system_proxy = true` 就能让后端认系统代理**，不需要替换 provider、不需要自定义 `base_url`。这是官方提供的、语义明确的开关。
2. **环境变量是永远可用的兜底** —— `ReqwestDefault` 策略下唯一被认可的路径。当系统代理会被其他软件抢来抢去时，环境变量方案反而更稳。
3. **策略是 per-client 构建期决定的**，所以改动配置后**必须重启客户端**才会生效；热重载不会重建已存在的 HTTP client。

## 六、适用边界

- `resolve_platform_system_proxy` 有 macOS 实现（`macos::resolve`，另有 `macos_system_proxy_configuration` 做不执行 PAC 的探测），所以这个开关在 macOS 上同样有意义。本项目的脚本目前只覆盖 Windows。
- 上游实现仍在演进（`UnderDevelopment`），字段名与默认值可能随版本变化。升级 Codex 后建议重跑 `Diagnose-CodexReconnect.ps1` 复核。

# 01 · 排查全过程

> 原始排查日期：2026-09-05
> 环境：Windows 11（10.0.22631）/ Codex 桌面版（商店包 `OpenAI.Codex`，内核 `codex-cli 0.153.x`）/ v2rayN 7.x（sing-box 内核，TUIC 节点，混合入站 `127.0.0.1:10808`）

本文是原始排查笔记的整理版，保留了当时的完整推理链，包括走过的弯路。想直接修请看 [README](../README.md)。

---

## 一、现象

ChatGPT 桌面客户端每次新开对话，发第一条消息后显示「正在重新连接 1/5 → 5/5」，重连满 5 次才开始正常回复。同一会话内之后一切正常，但每次新建会话都要重来一遍。

## 二、排查时间线

### 1. 社区线索：WebSocket 假说

在 linux.do 搜到多个同款问题帖，主流结论是：

- Codex 系客户端（含内置 Codex 内核的 ChatGPT 桌面版）**默认优先用 WebSocket 协议**与服务器通信；
- 代理链路对 WebSocket 不友好时，客户端重试 5 次（每次约 20 秒），全失败后才降级到普通 HTTP——正好对应「重连 5 次」的表象。

参考帖子：

- 《一步到位解决 codex 的 reconnecting 5 次才回复》<https://linux.do/t/topic/2161909>
- 《ChatGPT APP 总是提示"正在重新连接 1/5"》<https://linux.do/t/topic/2653201>

社区给的方案是改 `~/.codex/config.toml`，自定义一个 provider 并设 `supports_websockets = false`。

### 2. 第一次尝试：照搬社区方案 → 启动卡死

照帖子加上：

```toml
model_provider = "openai_https"

[model_providers.openai_https]
name = "OpenAI"
wire_api = "responses"
requires_openai_auth = true
supports_websockets = false
```

结果桌面客户端**卡在启动界面**。回滚备份后恢复。

复盘日志发现：卡死时段与正常启动时的错误几乎相同（都是插件目录同步失败类的 WARNING），真正的差异在**模型列表刷新超时**。结论：对桌面版来说，替换整个 provider 风险太高，放弃这条路。（但 `supports_websockets` 这个键在 0.153.x 内核里确实存在。）

### 3. 关键证据：后端进程根本没走代理

直接查客户端日志库 `~/.codex/logs_2.sqlite`，发现所有发往 `chatgpt.com` 的请求都在报：

```
error sending request for url (https://chatgpt.com/backend-api/ps/plugins/...)
```

但用 `curl -x http://127.0.0.1:10808 https://chatgpt.com` 测试，代理链路本身是通的。

**矛盾点**指向：Codex 的 Rust 后端进程没有使用 Windows 系统代理。

### 4. 读源码定性

拉 `openai/codex` 源码（tag `rust-v0.153.4`），确认三个事实：

1. `codex-rs/http-client/src/outbound_proxy.rs` 定义两种出站策略：
   - `ReqwestDefault`（默认）：只认 `HTTP_PROXY / HTTPS_PROXY / ALL_PROXY` 环境变量，**完全不读 Windows 注册表里的系统代理**；
   - `RespectSystemProxy`：先走 WinHTTP 解析系统代理 / PAC，再退回环境变量，最后直连。
2. 策略由特性开关决定（`codex-rs/core/src/config/mod.rs`）：

   ```rust
   let respect_system_proxy = features.enabled(Feature::RespectSystemProxy);
   ```

   `Feature::RespectSystemProxy` 的 key 是 `respect_system_proxy`，**默认 false**（`codex-rs/features/src/lib.rs`）。
3. 自定义 provider 不写 `base_url` 也没关系：ChatGPT 登录模式下会默认补 `https://chatgpt.com/backend-api/codex`。

### 5. 对照实验

| 测试 | 结果 |
| --- | --- |
| 只开 `respect_system_proxy = true`，无环境变量 | 仍在 Reconnecting（当时系统代理实际是关的，见下） |
| 显式设置 `HTTPS_PROXY=http://127.0.0.1:10808` | **模型请求秒回**，无重连等待 |

第二个实验直接证明：只要后端请求走了代理，重连问题立即消失。

### 6. 又一层真相：系统代理被关了

用 PowerShell 检查注册表：

```
ProxyEnable = 0                ← 系统代理被关了
ProxyServer = 127.0.0.1:7688   ← 还是别的工具留下的旧端口
```

也就是说除了「内核不读系统代理」，当时系统代理本身就处于断开状态。**两层问题叠加。**

## 三、最终修复（已验证）

1. **恢复系统代理**：`ProxyEnable=1`，`ProxyServer=127.0.0.1:10808`（v2rayN 混合入站端口）。
2. **`config.toml` 打开官方开关**（全部改动只有一行）：

   ```toml
   [features]
   js_repl = false
   respect_system_proxy = true
   ```

3. 重启 ChatGPT 桌面客户端。

**验收**：新建对话发送测试消息，约 6 秒收到回复，全程无重连提示，历史会话完好。

## 四、复盘要点

- 「重连 5 次才回复」的完整因果链：Codex 后端默认不读系统代理 → 直连被墙 → 请求反复失败 → 客户端重试降级 5 次。和社区说的「WebSocket 不被代理支持」是同一现象的不同侧面，但根因是**代理从未生效于后端进程**。
- 社区方案（替换 provider）对 CLI 有效，对桌面版有启动卡死风险；官方特性开关 `respect_system_proxy` 是更干净的路。
- 改 Codex 配置前先备份 `config.toml`。它的历史会话按 provider 分组存储，乱动 provider 会让旧会话「消失」（改回去即可恢复，不会真丢）。
- 以后若复发，先检查两件事：代理客户端的「系统代理」开关是否还开着；`[features]` 里的开关是否还在。

## 五、遗留事项

- `respect_system_proxy` 被 OpenAI 标记为 under development（`Stage::UnderDevelopment`），启动日志会有黄色警告。上游警告文案本身提示了消除方式：在配置文件里设**顶层键** `suppress_unstable_features_warning = true`（不在 `[features]` 表内）。
- 插件目录（`ps` / `mcp`）的 WebSocket 通道在代理下仍偶有报错，与聊天无关，可忽略。

## 六、顺带查清：系统代理为什么变成 7688

修复当天发现注册表里系统代理端口残留为 `127.0.0.1:7688` 且被关闭。追查结论：

**7688 属于某机场官方客户端**（内嵌 mihomo，`runtime.yaml` 中 `mixed-port: 7688`）。当天 11:24–11:27 该客户端运行过（应用数据文件时间戳为证），它把系统代理改指自己，退出时又把系统代理开关关掉、端口字段残留 7688。

而 v2rayN 7.x 没有任何守护逻辑——查源码确认：系统代理只在**核心启动 / 切换时设置一次**（`ServiceLib/Handler/SysProxy/SysProxyHandler.cs` 的 `UpdateSysProxy()`），之后被改不会自动恢复。

处理：新版 v2rayN 已移除「系统代理守护」选项，改为自建等效守护。这部分独立成了配套项目：

**[v2rayn-proxy-guard](https://github.com/cg689/v2rayn-proxy-guard)**

根本性建议：订阅已导入 v2rayN 的话，机场客户端如无必要可卸载；如需保留，避免与 v2rayN 同时开启系统代理。
